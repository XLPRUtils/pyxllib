# AGENTS.md

本目录是一个 Windows 上运行的网课考勤与返款中台，服务对象主要是惟海法师相关网课的日常考勤工作。

目标读者是第一次接手本项目的 AI 助手。先建立正确心智模型，再开始改代码。

## 1. 项目本质

这不是纯数据库项目，也不是纯 WPS 脚本，而是：

- `小鹅通后台 + 本地数据库 + WPS 在线表 + 微信支付 + 自建问卷 + 微信提醒` 的混合工作流
- 运行环境强依赖 Windows 本机登录态，尤其是浏览器、微信、微信支付
- repo 里主要是 Python 业务逻辑和本地版 AirScript 源文件；真正运行中的部分逻辑在远端 WPS 脚本和外部数据库里

核心链路通常是：

1. `KqTools` 用 DrissionPage 登录小鹅通，导出用户、课次、打卡等数据
2. `KqDb` 把导出的文件整理进数据库表，如 `user_table`、`lesson_table`、`clockin_table`、`clockin_data_table`、`weipay_table`
3. `KqCourse.step2()` 从数据库拼出某门课的考勤数据，写回对应 WPS 在线表的 `报名表`、`考勤表`
4. 远端 WPS 脚本 `kqcourse.js` 负责 `step3` 的应返款计算、`step5` 的已返款刷新、状态标记等
5. `KqCourse.step4()` 基于 `考勤表.当前应返款`、`报名表.商户订单号` 和名称管理器返款参数生成返款 CSV，再驱动微信支付执行返款；考勤表不再保留商户订单号列
6. `KqCourse.step6()` 发送日报；`kqbook.js` 和 `kqmain.py` 还负责总表、新版问卷提醒、退款检查等外围工作

## 3. 关键分层

### 3.0 课程 ABC 独立体系（统一术语）

A/B/C 是三套差异很大的独立业务体系，不是同一套考勤算法的三个参数分支。课程配置、采集、完成判定、更新时间、返款、工作簿和调度逻辑均按体系分别理解。只有与课程语义无关的基础设施可以默认复用；业务逻辑跨体系复用前必须逐项验证。

- **A 类课程**：普通觉观、念住的每月网课，使用普通时长/进度规则，`video_duration` 必需。
- **B 类课程**：禅宗、修道班，使用 Zen Stage 规则；只有实际进度达到 100% 或小鹅通标记“已完成”才进入完成判断，不依赖 `video_duration`，通常按周更新并可复用同阶上一期配置。累计观看时长不能替代完整看完；不足 100% 的进度只显示无底色的整数百分比，返款为 0，只有准时完整看完才返该课完整金额。
- **C 类课程**：闯关课程，使用独立的闯关进度/遍数规则。

开发、排障和配置迁移时必须先确认 A/B/C 体系，再进入该体系自己的流程，不得拿另一体系的字段清单或模板做默认基线。普通念住月课属于 A 类；明确的念住闯关属于 C 类。详细约定见 CodeYun `docs/考勤课程ABC分类约定.md`。

B 类内部也没有统一返款金额，各阶次规则分别确定。考勤表第 3 行“视频应返款”备注（如 `39课×18元=702元`）是 Step 3 的业务规则来源，必须解析并校验计费课数、单课金额、上限及视频配置课次数；解析失败或不一致必须阻断，禁止回退到 A 类默认值或其他阶次金额。

### 3.1 Python 基础层

`pyxllib/src/kq5034/` 里的几类对象是基础设施：

- `XiaoetongApi`：小鹅通开放 API，主要用于店铺 1 用户数据
- `XiaoetongWeb`：小鹅通网页端爬虫，负责导出用户、课次、打卡、检索用户
- `Weipay`：微信支付页面自动化，负责检索订单和执行返款
- `KqDb`：数据库读写层
- `KqBook`：考勤总表对应的 WPS 在线文档
- `KqTools`：把上面这些能力聚合起来

### 3.2 课程层

`courses/kqcourse.py` 的 `KqCourse` 是统一框架，典型流程是六步：

1. `step1` 下载小鹅通最新课次/打卡数据
2. `step2` 从数据库整理考勤文本并写入在线表
3. `step3` 在 WPS 里计算视频应返款
4. `step4` 自动返款
5. `step5` 刷新已返款
6. `step6` 发送日报

每个 `courses/d*.py` 文件通常只改这些点：

- `__init__`：课程名、店铺、`book_id`、`script_id`、回放天数、商品名
- `step2`：该课程如何拼接打卡列和课次列
- `step6`：日报发到哪个群、模板怎么套
- `开课配置` / `配置打卡数据` / `从旧课程数据迁移配置`：开新班时的一次性操作

### 3.3 WPS 脚本层

有两个本地 JS 源文件：

- `courses/kqcourse.js`：单课程在线表
- `kqbook.js`：总表

重要事实：

- repo 里的 JS 文件不是“改完自动生效”
- 真正在跑的是远端 WPS 脚本，靠每个表格的 `script_id` 关联
- 新班开课时，通常需要把本地最新 `kqcourse.js` 手动复制到对应在线表

不要误以为只改本地 JS 文件就能立刻影响线上表格。

## 5. 调度与运行节奏

`kqmain.py` 是全局例常入口：

- `每日早晨例常1()`：新版问卷提醒、用户数据、微信支付账单
- `每日早晨例常2()`：课程数据更新、普通课程返款、周日禅宗返款
- `每日晚上例常()`：晚间课程数据更新
- `每日凌晨例常()`：周日禅宗凌晨跑数、闯关类更新

这里的课程清单是硬编码 import 的。一个课程是否已接入正式调度，要看它有没有被 `kqmain.py` 引用。

另外，`KqCourse` 的状态不是本地文件，而是远端 WPS 表里的状态文本：

- `getStatus()` / `setStatus()` 由 `kqcourse.js` 维护
- 状态按天生效，隔天会被视为过期
- 梵呗类课程经常分成 `main_a()` 当天跑 `1~3`，`main_b()` 次日跑 `4~6`

改状态逻辑前先确认课程是不是依赖这种“跨天接力”。

### 5.1 网课完结标记

以后如果用户说这些话，按同一类需求理解：

- “这个网课完成了”
- “给这个网课做完成标记”
- “把这门课从日常调度里摘掉”

禅宗课完结不是只改一个地方，标准动作按下面清单做：

1. 在 `lesson_table` 中，把该网课对应全部课次的 `next_update` 统一设置为 `9999-12-31 23:59:59.000`，确保后续不会再进入课次更新队列。操作前先导出或记录该课程原始 `lesson_name / next_update` 快照，便于回滚。
2. 更新 CodeYun 考勤汇总表：
   - 把课程标记为完结，移动到白色正在运行课程后面的灰色完结区域。
   - 填写完结日期。
   - 统计 `报名费`、`报名人数`、`退课人数`、`已返款` 等字段，保留汇总表中 `实际总报名费`、`剩余促学金`、`返款率` 的当前行公式。
3. 统计禅宗课程汇总数据时，不要按 `考勤表` 全量行数算报名人数。正规报名口径以 `报名表.商户订单号` 非空为准：
   - `报名人数` = `报名表` 中 `商户订单号` 非空的行数。
   - `报名费` 通常取这些正规报名行的 `订单金额` 单价；若存在多种金额，先人工确认口径，不要直接取第一行。
   - `已返款` = 用这些正规报名行的 `商户订单号` 去 `考勤表` 匹配后，汇总匹配行的 `已返款`。不要把没有 `商户订单号` 的旁听、迁移、补录或异常行的 `已返款/总应返款` 算进汇总。
   - `实际总报名费` 应与 `报名人数 * 报名费` 对齐，必要时同时核对正规报名行的 `订单金额` 合计。
4. 把该课程脚本从 `courses/` 移到 `courses/已完结/`。如果使用 CodeYun 的批量整理函数，注意它可能会顺手移动其他已完结课程；非本次目标课程要移回去，避免扩大操作范围。
5. 在 `kqmain.py` 中，把该课程从调度清单里删除。禅宗课通常集中在 `禅宗类型` 列表中；该列表会同时影响 `每日早晨课程任务` 和 `每日凌晨课程任务`，删列表项即可同时摘掉持续监控和更新。若以后改回显式 `import` / `run_it(...)` 写法，也要同步删除对应 import 和运行项。

注意：

- 用户口头如果说“`kq5034.py` 里删掉”，当前项目里实际对应的是 `kqmain.py`。
- 这里要求是“删除代码行”，不是只注释掉。
- 做这类操作时，先同时检查课程清单、`import` 和 `run_it(...)` / 直接调用行，避免只删一半导致运行时报错。
- 修改后至少复核这些结果：目标课次 `next_update` 的最小值和最大值都为 `9999-12-31 23:59:59`；汇总表目标行的报名人数/已返款符合 `商户订单号` 口径；目标课程脚本只存在于 `courses/已完结/`；`kqmain.py` 不再包含目标课程名；如果考勤行为树服务正在运行，要重启或确认它会在下次启动加载新配置。

## 6. 数据模型里最重要的几点

- `lesson_table`：课次配置，包含 `lesson_id2`、开课时间、视频时长、`next_update`
- `lesson_data_table`：每个用户每堂课的观看数据
- `clockin_table`：打卡配置
- `clockin_data_table`：打卡明细
- `user_table`：用户基础资料
- `weipay_table` / `weipay_matview`：微信支付账单与检索视图

注意：

- `clockin_table.url` 不一定是单个字符串，也可能是 JSON 数组；`update_clockin()` 支持合并多个打卡链接
- 禅宗类打卡，尤其 `4点5阶`、`四阶` 这类长周期任务，可能在小鹅通页面里拆成 `第1-60天`、`第61-88天` 这种多段任务；数据库里需要把多个 URL 作为 JSON list 一起存到同一条 `clockin_table.url`
- `write_rows_skip_empty()` 会故意跳过 `user_id2` 为空的行，不能随便改成全表覆盖
- 课程文件里经常带少量“特判”或手工修正，很多是业务补丁，不是无意义冗余

## 7. 新功能或新课程怎么加

推荐顺序：

1. 先找一个最近、最像的课程脚本复制
2. 修改 `__init__` 里的 `shop_id`、`course_name`、`book_id`、`script_id`、`回放天数`、`课程商品名`
3. 确认数据库里已有该课的 `lesson_table` / `clockin_table` 配置
4. 没有课次配置时，优先用 `add_book_lessons_to_db()` 或“从旧课程迁移配置”
5. 没有打卡配置时，用 `update_clockin(..., url=..., download=False)` 先把 URL 记进数据库
6. 把最新 `kqcourse.js` 同步到对应 WPS 在线表，执行初始化动作
7. 先单独跑这门课的 `step1~step6` 或 `main_a/main_b`
8. 稳定后再接入 `kqmain.py`

如果只是修一个已有课程的小问题，不要第一步就去改全局调度。

## 8. 调试建议

优先做单课程、单步骤验证：

- 用户匹配问题：先看 `报名表` 的 `用户ID`、`匹配得分`，再看 `更新用户匹配()`
- 考勤异常：先看数据库 `browser_clockin_data()`、`browser_lesson_data()` 的输出，再看 `step2`
- A 类觉观/念住某一课视频数据为 0：先怀疑 `lesson_table.lesson_id2` 或 CodeYun `视频配置.lesson_id2` 配到了小鹅通同名空资源。相邻课次正常时，不要先猜权限或调度；去小鹅通直播列表等页面稳定后找同名候选，并用用户列表接口的 `total` 对比确认正确资源。
- 应返款异常：先看 `step3` 用的是哪种 WPS 函数，再看表里的公式结果
- 已返款异常：先看 `step5_更新已返款` 和 `weipay_matview`
- 退款/返款异常：先看 `当前应返款`、名称管理器里的返款参数、本地生成的返款 CSV、微信支付执行结果
- 问卷滞留提醒异常：同时检查 `kqmain.py` 和 `pyxllib/src/kq5034/questionnaire.py`
- 禅宗打卡次数明显偏少：先看小鹅通页面是否其实有多个任务分段，再看 `clockin_table.url` 是不是漏配成单 URL；细节见 `docs/clockin-multi-url.md`

如果用户说“某人没匹配上”或“某课没返款”，通常按这个顺序排查：

1. `报名表` 是否已有正确 `用户ID`
2. `考勤表` 是否同步到了该 `用户ID`
3. `step2` 写入的打卡/课次文本是否正确
4. `step3` 之后 `视频应返款` 是否正确
5. step4 能否按 `学号/序号` 从报名表反查 `商户订单号`，再用 `当前应返款` 和名称管理器生成返款 CSV 行
6. `weipay_matview` 是否能查到订单和已返款额度

## 9. 常见坑

- 只改 Python，不检查远端 WPS 脚本是否同步
- 只看 repo，不看数据库和 `D:\home\chenkunze\data\m2112kq5034`
- 把 `courses/已完结` 里的旧写法当成当前规范
- 修改 `step2` 时忽略空 `user_id2` 行的保留语义
- 看到小鹅通打卡页里有两段或多段任务，却只在数据库里保留了第一段 URL，导致导出数据长期偏少
- 小鹅通直播列表和详情页是重前端页面，不能点“管理”后立刻读新 tab URL 再马上关闭。必须等待列表行、详情 URL、关键按钮或接口包稳定；排查同名直播资源时优先复用一个工作页或直接抓列表接口。
- 觉观/念住月课容易出现同名直播资源错配：正常资源、测试资源、封禁素材资源可能标题和时间相近。若某课用户列表 `total=0` 而相邻课次有数据，应在列表中对比 `view_count`、素材状态、包关联和用户列表 `total`，再更新 `lesson_id2`。
- 以为所有课程都能直接套同一套日报/返款节奏，实际上梵呗、禅宗、闯关差异很大
- 忽视 Windows 本机登录态；很多功能依赖浏览器、小鹅通、微信、微信支付当前是已登录状态
- 看到中文命名就想英文化重构，这会直接提高维护成本并破坏既有业务语义
- 旧问卷网站自动化已经下线；新版问卷滞留提醒逻辑在 `pyxllib/src/kq5034/questionnaire.py`

这份文档的核心目的只有一个：

让后来者第一时间知道，这个项目不是“写几个 Python 函数处理 Excel”，而是在 Windows 本机上，协调小鹅通、数据库、WPS、微信支付、自建问卷和微信群消息，完成真实的考勤与返款工作。
